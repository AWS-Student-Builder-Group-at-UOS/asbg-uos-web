## 자격증부터 커뮤니티까지

리더 손수빈은 작년 2학기부터 클라우드에 관심을 가지고 자격증 공부를 먼저 시작했습니다. 이후 서버리스 아키텍처에 흥미를 느껴 AWS 한국사용자모임 세미나에 참석했고, 그 경험이 이번 커뮤니티 개설로 이어졌습니다. 현재는 9월부터 DevOps 직무 인턴을 하며 쿠버네티스를 공부하고 있습니다. 오늘 킥오프 세션은 이 소개로 시작해서, 앞으로 한 학기 동안 ASBG UOS가 무엇을 하고 왜 하는지를 먼저 그림으로 보여주는 자리로 진행됐습니다.

## ASBG UOS란 무엇인가

ASBG는 AWS Student Builder Group의 약자로, AWS가 운영하는 글로벌 학생 커뮤니티 프로그램입니다. AWS를 공부한다고 하면 콘솔에서 EC2나 S3 같은 서비스를 하나씩 눌러보는 장면을 먼저 떠올리기 쉽지만, 실제로 필요한 것은 서비스를 어떻게 설계하고 배포하고 운영할지까지 경험하는 일입니다. 그래서 ASBG는 세 가지 방향을 중심에 둡니다.

- **Learn** — AWS 서비스가 무엇이고 어떤 상황에서 쓰는지 공부합니다.
- **Build** — 직접 만들어보면서 각 서비스의 역할을 몸으로 확인합니다.
- **Connect** — 서로 만든 것을 공유하고, 진로와 기술 고민을 나눕니다.

ASBG UOS는 SW중심대학사업단장 김민호 교수님의 승인을 받아 정식으로 활동을 시작했으며, 나비스트 프로젝트 활동 팀으로도 선정되어 이번 학기 활동을 이어갑니다.

## 다섯 번의 세션, 하나로 이어지는 흐름

이번 학기 정기 세션은 아래 일정의 화요일에 총 5회 진행합니다. 시간은 20:00–21:30, 장소는 100주년기념관 나동 602호입니다.

| 일정 | 주제 |
|---|---|
| 9/8 | 킥오프 |
| 9/29 | VPC · EC2 · ALB · RDS |
| 11/3 | Lambda · DynamoDB · SQS |
| 11/24 | ECS · ECR · CodePipeline |
| 12/29 | 종합 점검 (SAA 문제 바탕) |

서비스 이름만 나열하면 복잡해 보이지만, 하나의 웹 서비스를 완성해 간다고 생각하면 흐름이 자연스럽습니다. 사용자의 요청을 처리할 서버(EC2)를 VPC 안에 두고, 트래픽이 몰릴 때 여러 서버로 나눠주는 ALB를 붙이고, 데이터를 저장할 RDS를 연결하면 3-Tier 구조 하나가 완성됩니다. 11월 세션에서는 이 구조에서 한 걸음 나아가 AWS가 인프라 운영을 대신 맡아주는 서버리스·이벤트 기반 구조(Lambda·DynamoDB)와, 처리를 뒤로 미뤄 서비스 간 결합도를 낮추는 큐(SQS)를 다룹니다. 마지막으로 11월 24일 세션에서는 컨테이너(ECR·ECS)로 실행 환경 차이를 줄이고, CodePipeline으로 배포까지 자동화하는 CI/CD를 경험합니다.

![킥오프에서 종합 점검까지 다섯 세션이 하나의 서비스로 이어지는 흐름](img/diagram.svg)

정리하면 학기 전체는 "네트워크와 서버 → 서버리스와 이벤트 → 컨테이너와 자동 배포" 순서로, 점점 실제 서비스 운영에 가까워지는 구조로 짜여 있습니다.

## 정기 세션 밖의 활동

정기 세션 외에도 두 가지 활동이 더 있습니다. 10월 2일(금)에는 네트워킹 모임이 예정되어 있는데, AWS 이야기만 하는 자리가 아니라 서로 교류하고 진로를 상담하고 AI 활용법을 공유하는 자리로 준비하고 있습니다. 또한 SAA 같은 자격증 공부를 하고 싶은 사람이 직접 스터디를 열고 운영할 수 있는 자율 스터디도 운영합니다. 코어팀이 모든 활동을 정해주는 방식이 아니라, 하고 싶은 사람이 직접 모임을 만들 수 있는 구조를 지향합니다. 타대학 리더분들과의 세션과 현직자 연사 세션도 추진 중이며, 확정되면 화요일 정기 세션과는 별도로 안내할 예정입니다.

## 실습 비용 지원

AWS를 직접 사용하면 비용이 발생할 수 있는데, ASBG UOS는 나비스트 프로젝트로 선정되어 세션 과제 실습에 사용한 비용을 실제 청구액 기준으로 지원합니다. 지원 한도는 한 학기 1인당 최대 60,000원이며, 초과분은 개인이 부담합니다. 비용이 무서워서 실습을 안 하는 일이 없도록 마련한 제도이지만, 리소스를 켜놓은 채 방치하면 예상치 못한 비용이 쌓일 수 있으므로 실습이 끝나면 리소스를 정리하는 습관도 함께 강조하고 있습니다. 장기간 켜두는 서버 비용보다는, 평소 써보기 어려운 다양한 서비스를 실습해보는 데 이 지원을 활용하는 것을 권장합니다.

## 과제는 자율, 기록은 남게

과제 참여는 자율입니다. [1기 과제 저장소](https://github.com/AWS-Student-Builder-Group-at-UOS/cohort-01-assignments)의 고정 템플릿 네 항목 — What I Built, Design Decisions, Troubleshooting, Screenshots — 을 Markdown으로 작성해 **1인·1회차·1PR**로 제출합니다. `images/`에는 아키텍처 다이어그램과 실제 결과 화면을 각각 1개 이상 넣고, 추가 이미지를 포함해 모두 제출 README에 첨부합니다. 리뷰는 코어팀을 중심으로 진행하며 일반 멤버도 참여할 수 있습니다. 제출자는 같은 PR에서 답변하거나 수정하고, 손수빈(`ssub17`)의 최종 승인 후 코어팀이 머지해 학습 기록으로 남깁니다.

평가는 완료 조건 충족, 구성·설정의 선택 근거, 검증·문제 해결 과정을 기준으로 합니다. 문제가 없었다면 Troubleshooting에는 `없음`을 적고 Screenshots에 정상 동작을 확인한 방법과 결과를 남기면 됩니다. 문제 발생 여부는 가감점 사유가 아닙니다. 우수 과제는 공지된 기준에 따라 선정하며, 1등은 스타벅스 1만 원권, 2등은 5천 원권을 받습니다. 제출 방법과 마감·평가 안내는 과제 저장소에서 확인할 수 있습니다.

## 수료 조건과 혜택

수료 조건은 5회 세션 중 4회 이상 출석입니다. 10분부터는 지각으로 처리되고, 지각 2회는 결석 1회로 계산됩니다. 출석을 기준으로 두는 이유는 단순한 관리 목적이 아니라, 커뮤니티 프로그램의 장점이 직접 참여해서 함께 듣고 질문하고 다른 사람이 만든 것을 보는 데 있기 때문입니다. 그래서 수료 조건인 4회보다는 5회 모두 참여하는 것을 권장합니다.

수료자에게는 자격증 시험 바우처와 수료증이 제공됩니다. 바우처는 CLF(AWS Certified Cloud Practitioner)부터 지원하며, 이미 CLF를 취득했다면 SAA를 요청할 수 있습니다. 자격증 취득 자체보다는 실습 → 개념 이해 → 자격증 공부 순서로 연결해보는 쪽을 추천합니다. 직접 EC2 여러 대를 구성하고 ALB를 붙여본 뒤 "ALB는 트래픽을 분산한다"는 문장을 다시 읽으면 이해도가 확실히 달라집니다.

## AWS Builder Center 가입은 지금

AWS Builder Center는 이번 활동에서 공식적으로 활용하는 학습 플랫폼입니다. 지금 가입하면 학생 인증 이벤트에 참여할 수 있고, 워크숍 스튜디오의 핸즈온 가이드도 바로 활용할 수 있습니다. 새로 추가된 **Student Rewards** 프로그램은 학생 인증과 활동 뱃지에 따라 아래와 같은 혜택을 제공합니다.

| 조건 | 혜택 |
|---|---|
| 학생 인증 + 프로필 완료 | AWS Skill Builder Premium 12개월 |
| Badge 7개 | AWS Credit $10 |
| Badge 14개 | AWS Credit 추가 $20 |
| Badge 21개 | AWS Foundational Certification 시험 바우처 |

Badge 21개까지 모으면 총 $30의 AWS Credit과 $100 상당의 Foundational Certification 시험 바우처를 받을 수 있고, Skill Builder Premium 12개월은 900개 이상의 교육 과정과 핸즈온 랩, 자격증 준비 콘텐츠를 포함한 $449 상당의 혜택으로 안내되어 있습니다. 아직 가입하지 않았다면 [builder.aws.com/learn/students](https://builder.aws.com/learn/students)에서 가입할 수 있습니다.

## 다음 세션 예고 — 3-Tier 웹 서비스 구축

다음 세션은 9월 29일(화), 주제는 3-Tier 웹 서비스 구축입니다. 다루는 서비스는 VPC, EC2, Auto Scaling, ALB, RDS이며, 핵심 질문은 "트래픽이 갑자기 몰려도 서비스가 죽지 않으려면 어떻게 해야 할까"입니다. 서버 한 대로 버티다가 갑자기 몰리는 트래픽에 무너지는 상황을 가정하고, 여러 서버에 트래픽을 나누는 ALB, 필요할 때 서버 수를 늘리는 Auto Scaling, 애플리케이션 서버와 분리해 관리하는 데이터베이스까지 직접 구성하며 단일 장애점(SPOF)을 찾아내고 개선안을 설계해 봅니다.
