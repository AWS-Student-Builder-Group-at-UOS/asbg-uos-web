## 오늘의 목표는 파일 하나를 제대로 읽는 것

Round 0의 두 번째 발표에서는 19:25부터 20:40까지 이예나가 실습 계정의 권한과 비용 점검을 맡았습니다. 앞 발표에서 터미널과 Git으로 작업을 남기는 방법을 익혔다면, 이번에는 AWS에서 어떤 자격으로 작업하는지 설명할 수 있어야 합니다. 화면에 로그인 버튼이 있고 서비스 목록이 보이는 것만으로 준비가 끝났다고 판단하지 않기로 했습니다.

출발점은 간단합니다. 팀원이 실습 안내 파일을 읽어야 하는데 계정 전체를 수정할 권한까지 필요할까요? 이번 예제의 성공 조건은 지정한 S3 경로의 파일을 읽고, 다른 경로를 읽거나 파일을 올리는 요청은 허용하지 않는 것입니다. 무엇이 성공하는지뿐 아니라 무엇이 실패해야 하는지 먼저 적으면 필요한 권한의 범위가 훨씬 분명해집니다.

이 글의 JSON은 정책을 읽어 보는 예제입니다. 운영진이 준비한 안내 파일을 기준으로 작업과 리소스 범위를 검토했습니다. 직접 따라 할 때에는 배정된 실습 환경에 맞게 버킷과 경로를 다시 확인해야 합니다.

## 로그인한 사람과 작업하는 역할 구분하기

IAM 역할은 특정 작업에 사용할 권한을 담는 AWS 자격입니다. 역할 자체에 일상적으로 공유하는 비밀번호나 장기 액세스 키를 만들어 두는 방식이 아니라, 허용된 주체가 역할을 맡으면 만료되는 임시 자격 증명으로 역할 세션을 사용합니다. 유효 기간은 로그인 방식과 설정에 따라 달라지므로 이 발표에서는 특정 시간으로 외우지 않습니다. [AWS IAM 역할 설명](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles.html)

시작 화면에서 확인할 것은 계정 이름, 선택한 역할, 현재 작업 대상입니다. 팀 문서에는 역할의 용도와 담당자를 적고, 콘솔 캡처에는 계정 ID와 개인 이메일을 가립니다. 임시 자격 증명도 유효한 동안에는 비밀정보이므로 채팅이나 Git 저장소에 붙이지 않습니다. 재로그인이 필요할 때 팀원의 값을 복사해서 해결하는 흐름도 실습 규칙에서 제외했습니다.

이 단계에서 팀원에게 물을 질문은 “접속됐어?”보다 구체적입니다. “지금 안내 파일을 읽는 요청은 어느 역할로 나갈까?”라고 묻고, 화면에서 찾은 역할 이름과 문서의 이름을 대조합니다. 두 이름이 다르면 정책을 수정하기 전에 로그인 경로부터 확인할 수 있습니다.

## 역할에 붙는 두 문서는 다른 질문에 답합니다

**신뢰 정책**은 누가 어떤 조건으로 역할을 맡을 수 있는지 정합니다. **권한 정책**은 그 역할을 사용해 어떤 작업을 어느 리소스에 요청할 수 있는지 정합니다. S3 읽기 권한을 추가했다고 역할 전환이 자동으로 허용되는 것은 아니며, 역할 전환이 성공했다고 모든 S3 객체를 읽을 수 있는 것도 아닙니다. [AWS의 신뢰 정책 설명](https://aws.amazon.com/blogs/security/how-to-use-trust-policies-with-iam-roles/)

화이트보드에는 입장과 작업을 두 줄로 나눠 적었습니다. 첫 줄은 “배정된 로그인 주체가 실습 역할을 맡는다”, 둘째 줄은 “그 역할이 안내 경로의 파일을 읽는다”입니다. 역할 전환 자체가 실패하면 첫 줄의 주체·조건을 확인하고, 전환 후 파일 읽기가 실패하면 둘째 줄의 작업·리소스를 확인하는 식입니다. 실제 평가는 계정 간 접근 여부와 정책 구성이 함께 작용하므로, 한 가지 정책만으로 모든 경우를 설명하려고 하지 않습니다.

신뢰 대상을 아무나 들어올 수 있도록 넓히는 수정은 이번 예제의 해결책이 아닙니다. 운영진이 정한 로그인 방식과 역할 배정을 먼저 확인하고, 변경이 필요하면 의도한 주체와 이유를 함께 검토합니다. 팀원들이 정책 JSON 전체를 암기하는 것보다 두 문서의 질문을 혼동하지 않는 것을 첫 번째 복습 기준으로 삼았습니다.

## Allow 한 줄만 찾고 끝내지 않기

IAM 요청은 기본적으로 허용이 없으면 거부되며, 요청에 적용되는 명시적 `Deny`는 `Allow`보다 우선합니다. 다만 리소스 정책이 누구에게 권한을 주는지, 같은 계정인지 다른 계정인지에 따라 세부 평가가 달라집니다. 따라서 앞의 도식은 검토 순서를 설명하는 것이며 AWS 내부 평가 알고리즘 전체를 대신하지 않습니다. [AWS 정책 평가 로직](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html)

권한 경계는 자격에 연결된 권한 정책이 부여할 수 있는 최대 범위를 제한합니다. 경계를 붙이는 것만으로 새 권한이 생기지는 않습니다. 조직의 SCP 역시 권한을 직접 부여하는 문서가 아닙니다. 예제에서는 조직 관리자가 제한을 담당하고, 참가자는 제한을 풀기보다 요청이 실습 목적에 맞는지 검토하는 역할을 맡습니다. [IAM 권한 경계](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html), [IAM 보안 모범 사례](https://aws.amazon.com/iam/resources/best-practices/)

진단 메모에는 먼저 주체, 작업, 리소스, 조건을 적습니다. 그다음 역할의 권한, 관련 리소스 정책, 적용되는 경계와 조직 정책을 확인할 담당자를 찾습니다. “S3가 안 돼요”라는 문장 대신 “실습 역할로 안내 경로의 객체 읽기를 요청했는데 거부됐어요”라고 적으면 다음 사람이 어디부터 봐야 할지 알 수 있습니다.

## S3 안내 경로만 읽는 작은 정책

아래 정책의 버킷 이름 `replace-with-your-workshop-bucket`은 교체가 필요한 자리표시자입니다. `workshop/round-0/` 안의 목록 조회와 객체 읽기만 예시로 허용합니다. 버킷 전체 탐색이나 업로드·삭제는 이 정책이 부여하는 권한에 포함되지 않습니다. 기존에 다른 권한이 붙어 있다면 그것까지 제한해 주는 정책은 아니므로 전체 구성을 함께 확인해야 합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListWorkshopPrefix",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::replace-with-your-workshop-bucket",
      "Condition": {
        "StringLike": {
          "s3:prefix": ["workshop/round-0/*"]
        }
      }
    },
    {
      "Sid": "ReadWorkshopObjects",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::replace-with-your-workshop-bucket/workshop/round-0/*"
    }
  ]
}
```

목록 조회는 버킷 ARN에 적용하고 `s3:prefix` 조건으로 요청 범위를 좁힙니다. 객체 읽기는 뒤에 객체 경로가 포함된 ARN을 사용합니다. 별표를 무조건 지우는 것이 목표는 아닙니다. 여기의 별표는 합의한 경로 아래 객체를 뜻하며, 버킷 이름이나 허용할 작업 전체를 대신하지 않습니다. [S3 자격 기반 정책 예제](https://docs.aws.amazon.com/AmazonS3/latest/userguide/example-policies-s3.html), [S3 prefix 조건 예제](https://docs.aws.amazon.com/AmazonS3/latest/userguide/amazon-s3-policy-keys.html)

검토할 요청은 네 개입니다. `workshop/round-0/`로 목록을 요청하는 경우, 그 안의 `guide.txt`를 읽는 경우, `workshop/round-1/`의 파일을 읽는 경우, 안내 경로에 새 파일을 쓰는 경우입니다. 이 정책 외의 허용과 별도 거부가 없는 예제 조건에서 앞의 두 요청은 허용 대상이고 뒤의 두 요청에는 허용이 없습니다. 요청한 경로의 철자와 끝의 슬래시도 메모에 그대로 남깁니다.

이 JSON은 콘솔의 모든 화면을 탐색하기 위한 정책이 아닙니다. 콘솔은 추가 조회 권한을 요구할 수 있고, KMS 키로 암호화된 객체 등 다른 구성이 있으면 별도의 권한 검토도 필요합니다. 예제에서 성공을 예상한 작업이 실패했다면 실제 요청과 저장 방식을 확인한 뒤 필요한 차이만 검토합니다. [S3 정책 작성 시 고려 사항](https://docs.aws.amazon.com/AmazonS3/latest/userguide/example-policies-s3.html)

## 실습에서 만난 AccessDenied, 서로 다른 확인 순서

팀별로 막힌 지점을 모으니 AccessDenied라는 이름은 같아도 확인할 곳은 달랐습니다. 에러 메시지를 곧바로 원인으로 받아들이지 않고, 관찰과 가설을 분리해서 기록했습니다.

| 관찰한 상황 | 먼저 확인한 사실 | 함께 확인한 결론 |
|---|---|---|
| 역할을 선택하는 단계에서 실패 | 아직 S3 요청은 보내지 않았음 | 로그인 주체와 역할 배정, 신뢰 조건부터 확인 |
| 객체 주소로는 읽히지만 목록은 거부 | 목록 요청의 prefix가 빈 문자열이었음 | 허용한 `workshop/round-0/`를 지정해 재검토 |
| 다른 라운드 파일 읽기가 거부 | 요청 경로가 `workshop/round-1/guide.txt`였음 | 이번 범위 밖이므로 예상한 결과로 기록 |
| 안내 경로에 파일 쓰기가 거부 | 요청 작업이 읽기가 아닌 쓰기였음 | 읽기 전용 실습이므로 권한을 추가하지 않음 |

목록 조회가 막힌 팀의 첫 제안은 버킷 전체를 보게 하자는 것이었습니다. 리뷰에서는 목록을 보려는 목적과 요청한 경로를 먼저 대조했습니다. 안내 경로만 필요하다면 빈 prefix를 보낼 이유가 없었고, 정책을 넓히지 않아도 요청을 바로잡을 수 있다는 결론을 적었습니다. 반대로 안내 파일 자체의 위치가 잘못됐다면 정책 문제가 아니라 실습 자료를 준비한 쪽에서 수정해야 할 수 있습니다.

마지막에는 성공 화면만 남기는 제출 방식을 바꿨습니다. 요청의 작업과 경로, 예상 결과, 확인한 결과, 다음 행동을 다섯 칸으로 적습니다. 의도한 거부도 완료 근거에 포함하고, 아직 원인을 찾지 못한 항목은 확인한 사실까지만 씁니다. 추측으로 “SCP 문제”라고 단정하지 않는 것이 이 기록 양식의 핵심입니다.

## MFA와 예산 알림을 연결해서 점검하기

루트 사용자는 일상 실습에 사용하지 않고, 계정 소유자가 MFA와 복구 수단을 안전하게 관리하는 구성을 확인합니다. MFA 등록 과정의 비밀값이나 복구에 필요한 정보를 제출물에 담지 않습니다. 참가자 로그인 경로의 MFA도 운영진이 지정한 인증 체계에서 확인하며, 루트 MFA가 있다는 사실만으로 모든 로그인 경로의 확인을 끝내지 않습니다. [AWS 루트 사용자 모범 사례](https://docs.aws.amazon.com/IAM/latest/UserGuide/root-user-best-practices.html)

예산 알림은 비용이 목표에 가까워지거나 초과할 때 대응하기 위한 장치입니다. 비용 반영과 통지에는 지연이 있을 수 있어, 알림을 받기 전에 기준을 넘는 비용이 생길 수 있습니다. 알림만 설정했다고 결제 한도가 생기거나 리소스가 자동으로 멈추는 것은 아닙니다. [AWS Budgets 비용 추적과 알림](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html)

예시 운영안은 합의한 월 예산의 50%·80%·100%에서 담당자에게 알리고, 누가 확인해 무엇을 검토할지 기록하는 것입니다. 이는 AWS의 필수 기준이 아니라 이 발표에서 비교할 대응안입니다. 예산의 계정 범위와 포함 비용도 함께 확인해야 숫자를 같은 의미로 읽을 수 있습니다. AWS Budgets의 자동 작업은 별도 구성 기능이며, 알림을 등록하는 것과 구분해서 검토합니다. [AWS Budgets 작업 구성](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-controls.html)

알림 수신 주소를 적는 칸 옆에는 부재 시 확인할 사람도 적었습니다. 80% 알림을 받고 다음 모임까지 기다릴지, 당일 현재 비용과 남은 자원을 살펴볼지 합의가 없다면 알림은 받은 편지함에만 남습니다. 제출물에서는 예산 금액과 함께 담당자와 대응 순서가 분명한지를 확인했습니다.

## 종료 전 동료에게 설명해 보기

종료 시점에는 새로 만든 자료와 변경한 권한이 있는지 목록을 대조합니다. 별도 실습 환경에서 작업한 내용은 운영진의 정리 지침에 따라 대상과 담당자를 확인했습니다. 공유 버킷이나 공용 역할을 개인 실습 흔적으로 오해해 지우지 않도록 소유자 확인을 먼저 적었습니다. 정리 대상이 없더라도 “없음”을 확인한 범위는 남겨 둡니다.

동료 리뷰는 세 문장으로 진행합니다. 내 역할이 들어갈 수 있는 이유, 안내 파일을 읽을 수 있는 이유, 다른 경로는 이번 권한에 포함되지 않는 이유입니다. 문장이 정책과 어긋나면 그 부분을 다음 확인 항목으로 남깁니다. 운영진은 기록과 미해결 항목을 보고 다음 라운드 전에 함께 확인할 내용을 정리했습니다.

[실습 계정 점검표 PDF](files/workshop-checklist.pdf)를 사용하면 로그인, 정책 검토, 예상 결과, 예산 대응, 종료 확인을 한 번에 기록할 수 있습니다.

## 발표 뒤에 남긴 질문

**Q. 임시 자격 증명은 만료되니까 저장소에 올려도 괜찮나요?**

아닙니다. 만료 전에는 사용할 수 있는 자격 증명입니다. 제출물에는 자격 증명 대신 역할의 용도와 확인 결과만 남깁니다. 노출이 의심되면 만료를 기다리며 방치하지 않고 운영진에게 알려 현재 세션과 접근을 점검합니다.

**Q. 파일을 읽을 수 있는데 버킷 첫 화면이 안 열리면 실패인가요?**

이번 예제는 지정한 경로에 대한 제한된 요청을 기준으로 평가합니다. 어떤 화면에서 어떤 추가 요청이 실패했는지 확인하고, 그 화면 탐색이 실제 학습 목표인지 판단합니다. 편의를 위해 권한을 넓히기 전에 요청 범위를 맞출 방법부터 검토합니다.

**Q. 예산 100% 알림을 받으면 더는 비용이 안 나오나요?**

그렇게 가정하지 않습니다. 알림의 의미와 대응 절차를 다시 확인하고 현재 비용과 남은 작업을 살펴봅니다. 자동 작업을 구성한 경우에도 대상과 동작을 따로 검토해야 합니다.

**Q. 다음 라운드에 쓰기 권한이 필요하면 처음부터 추가해 둘까요?**

다음 과제의 작업과 대상이 정해졌을 때 이유를 남기고 변경합니다. 이번 읽기 과제의 검토 기준과 다음 과제의 기준을 각각 보존하면 언제 어떤 필요로 범위가 달라졌는지 설명하기 쉽습니다.
